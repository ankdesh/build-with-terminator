## Context
Currently, the `log-analysis-client` lacks a formalized CLI entry point that routes requests to either the interactive LLM planner (analysis mode) or deterministically executes a predefined sequence of operations (execution mode). A robust CLI will fulfill the project's goal of serving as a workflow engine (Control Plane) where instructions are declaratively defined.

## Goals / Non-Goals

**Goals:**
- Create a CLI entry point using a standard library (e.g., `argparse`).
- Support an `analysis` command: accepts a `--request` string and a `--log` file. (Implemented as a placeholder for now; full LLM Planner integration will follow).
- Support an `execute` command: accepts a `--workflow` YAML file and a `--log` file, parsing the YAML into an instruction trace and feeding it directly to the Orchestrator.
- Establish a `workflows/` directory to store reusable YAML templates.

**Non-Goals:**
- Modifying the core `Orchestrator` execution loop. We assume the Orchestrator already accepts instruction traces.
- Modifying the internal logic of the LLM Planner, just hooking up the CLI to it.

## Decisions
- **CLI Framework**: Use Python's built-in `argparse` to minimize external dependencies and keep the application lightweight, providing standard `--help` outputs.
- **YAML Parsing**: Use `PyYAML` to parse the workflow files into Python dictionaries, mapping cleanly to the `Instruction` format the Orchestrator expects.
- **Workflow Storage**: A `workflows/` directory at the project root will house standard workflows. The user will be required to provide the explicit file path (no automatic path resolution fallback).
- **Analysis Workflow Saving**: The `analysis` mode will currently just be a placeholder (e.g. dummy print statements). The integration with the LLM planner to save generated YAML traces to disk will be handled in a later change.

## Risks / Trade-offs
- **Risk**: The YAML structure provided by the user or generated by the LLM might be malformed.
  **Mitigation**: Implement strict validation of the YAML schema (e.g., ensuring `action` and `executor` keys exist) before passing it to the Orchestrator.
- **Risk**: LLM hallucination could generate invalid executors or actions.
  **Mitigation**: The CLI should catch Orchestrator validation errors early and gracefully report them to the user.
